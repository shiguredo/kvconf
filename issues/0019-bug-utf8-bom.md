# UTF-8 BOM 付きの設定ファイルで先頭キーが BOM 込みのキーとして扱われる

- Created: 2026-09-23
- Completed: YYYY-MM-DD
- Branch: feature/fix-utf8-bom
- Polished: 2026-09-23

## 目的

UTF-8 BOM 付きで保存された設定ファイルを読み込むと、先頭キーに BOM が混ざった別のキーとして扱われ、未知キーとして無言で通る。BOM の扱いを定めて修正する。

## 現状

- `kvconf` の `parse_lines/3` は BOM を除去せず、先頭行を通常の `key=value` 行として処理する
- 実測: `initialize([], <<16#EF, 16#BB, 16#BF, "key = value\n">>)` → `{ok, [<<16#EF, 16#BB, 16#BF, "key">>], []}` (`key` ではなく BOM 込みのキーが未知キーとして返る。エラーにはならない。`~p` では `<<"ï»¿key">>` と表示される)
- BOM の扱いを定めた記述は README / CHANGES / issues にない
- `issues/0006` (CRLF・タブ) は `parse_lines/3` のコメント・空白行判定を変更する。本 issue は `parse/1` のみを変更するため変更箇所は重ならない。0006 / 0010 / 0014 / 0018 も `kvconf.erl` の eunit にテストを追加するため、同じ `-ifdef(TEST)` ブロックの編集が衝突しうる (実装順の依存はない)

## 設計方針

- 先頭の UTF-8 BOM (`16#EF, 16#BB, 16#BF` の 3 バイト) を除去して受理する方式を採る。BOM は文字ではなく符号化方式の目印であり、BOM を付けて保存するエディタが実在するため、拒否すると既存の設定ファイルが読めなくなる (拒否方式は後方互換のない変更になるため採らない)
- 除去は `parse/1` の `binary:split/3` の前に行い、対象は `Binary` の先頭 3 バイトのみとする。`parse_lines/3` のコメント・空白行判定は変更しない (`issues/0006` との変更箇所の重複を避ける)
- 先頭以外に現れる BOM (2 行目以降の行頭、キーの途中) は除去せず、現行どおりキーの一部として扱う

## 完了条件

- `initialize([], <<16#EF, 16#BB, 16#BF, "key = value\n">>)` が `{ok, [<<"key">>], []}` を返す (先頭キーが `key` として扱われる)
- BOM だけの行で始まる設定ファイルも受理する。`initialize([], <<16#EF, 16#BB, 16#BF, "\nkey = value\n">>)` が `{ok, [<<"key">>], []}`、`initialize([], <<16#EF, 16#BB, 16#BF>>)` が `{ok, [], []}` を返す (BOM 除去後の先頭行は空行としてスキップされる)
- 先頭以外の BOM は現行どおりキーの一部として扱う (2 行目の行頭 BOM とキーの途中の BOM が BOM 込みの未知キーとして返る)
- 回帰テストが `kvconf.erl` の eunit に追加されている
- BOM 付きファイルで先頭キーが未知キーから既知キーに変わるユーザーに見える挙動変更を伴うバグ修正のため、CHANGES.md の develop セクションに [FIX] として追記する
